## 3. 新代码审计（上轮之后的 5 个 feature commit）

总体评价：质量与修复批次一致地好。speaking 模块的 azure.ts 封装干净、录音器 16kHz 参数正确、`finishScriptSession` 的"每句取最新 attempt"逻辑正确。以下按严重度列新发现（编号 R-x）。

### R1 · P1 — `scripts/` 整目录被 gitignore，仓库不再自包含

.gitignore 以"TCF 版权内容不入库"为由 ignore 了整个 `scripts/`，但目录里 16 个文件大多是**代码**而非内容：TCF 导入管线（import-tcf-\*.ts、parse 工具）、音频生成（generate-tcf-audio.py）、`reenrich-vocab.ts`。后果：

- `package.json` 的 `db:reenrich` 指向一个 git 里不存在的文件——fresh clone 直接坏；
- 电脑一坏，整条 TCF 导入管线（几周的工作量）无备份；
- 错题闭环 spec §6 计划的 `scripts/tag-tcf-questions.ts` 会掉进同一个坑。

**修复**（15 分钟）：gitignore 改为只 ignore 数据（`scripts/**/*.pdf`、`scripts/data/` 之类按实际情况），`git add scripts/*.ts scripts/*.py`。版权内容本来就在 `public/media/`（已单独 ignore）。

### R2 · P1 — 反馈 pending 态没有逃生出口

`createSubmission` 把 AI 调用放进 `after()`，但 `after()` 不持久——**dev server 重启 / 进程崩溃发生在生成期间，`feedback_status` 永远停在 `pending`**，反馈页无限转圈轮询（feedback-pending.tsx 每 4s refresh，无超时）。`regenerateFeedback` 明明已经存在，pending 分支却不提供它。

**修复**（半小时）：反馈页对 `pending && submittedAt 早于 3 分钟前` 的 submission 渲染 Retry（复用 FeedbackRetry）；或轮询组件计数 30 次后显示重试按钮。

### R3 · P2 — `/api/speaking/assess` 输入面未收口

全站唯一的 route handler（route.ts:38）：`sessionId` 未经校验直接拼进文件路径（`public/media/speaking/<sessionId>/`）——路径穿越面；音频体积无上限（整个 body 进 Buffer）；文件写盘发生在 DB 校验之前（非 uuid 的 sessionId 会先写文件再 500）。单用户本地跑实害极低，但这是暴露面最大的入口，修复是三行：UUID 正则校验 + `audio.size` 上限（如 10MB）+ 先校验后写盘。

### R4 · P2 — `npm run lint` 形同虚设

ESLint 扫描了 `.claude/worktrees/`（残留 worktree 里的第三方/生成代码），报 **8897 个问题，其中 8892 个是噪音**——真实项目只有 5 个。lint 已经无法用作提交前检查。**修复**：eslint.config.mjs 加 `ignores: [".claude/"]`。

### R5 · P3 — 780MB 残留 worktree

`vocab-memory`（777MB，分支早已合并）+ `youthful-booth-1abb64`（detached）。`git worktree remove` 清理，顺带消掉 R4 的一半根源。

### R6 · P3 — 文档系统性过时（对 AI 辅助开发是真实成本）

| 文件 | 声称 | 实际 |
|---|---|---|
| CLAUDE.md | "Sprint 3 complete，S4 是下一步"、"Six tables"、"node-postgres" | S1–S10+Speaking 已完成、**23 张表**、驱动是 **postgres.js**（db/index.ts:1-2）；env 缺 `AZURE_SPEECH_KEY/REGION` |
| README.md | "v0.1 (Sprint 1 complete)" | 同上 |

CLAUDE.md 是每个 AI session 的第一输入，它现在每次都在教错架构。**修复**（半小时）：按现状重写"项目状态/架构/表清单/env"四节；顺带把设计文档三处分散（docs/、docs/superpowers/{specs,plans}、docs/todo/）收敛出一个索引。

### R7–R11 · P3/P4 — 小项

- **R7**：exam-runner.tsx 里 `score` useMemo 与 `handleFinish` 各算一遍同样的 perLevel（#24 的续集）。

模式很清楚：**工程型任务（落库、音频、修复）执行率 100%，产品型任务（Readiness、密度、/today）执行率 0%。** 两个 0.5–1 天的产品项被三周的工程工作反复挤掉。这不是能力问题，是排期偏好问题——值得警惕，因为漏掉的恰恰是"让练习发生"的那一类。

### 4.2 错题闭环 spec（07-06）评审

设计质量高，多个取舍有明确记录（`correct` 冗余存储的理由、cascade delete 的接受条件、打标脚本幂等可续跑、退役 localStorage 并把答题历史当数据资产）。两点修改建议：

1. **拆开上线**：spec §10 的第 1 步（数据模型 + 落库路径，约 1 天）单独先发——它让 drill 数据从今天开始积累，且不依赖打标/队列/面板。后三步在数据积累的同时慢慢做。
2. **实施第 4 步（回顾页复用 ExamRunner）之前先做 #24 的题卡抽取**，否则 60% 重复代码获得第三个消费方。

一个方向性提醒：spec 把"北极星 = TCF Canada 长期备考"正式写下来了（上轮 F1 的前半个建议兑现）。但上轮总结的三个病根——方向未收拢 ✅ 已解决、**数据有进无出 ◐ 只修了"进"**（TCF 落库了，出口 Readiness/复习队列仍无）、**缺编排层 ❌ 未动**。错题闭环继续在"进"上加码，"出"和"编排"仍然空着。

### 4.3 本次最重要的产品判断

上轮说"产品的问题不是功能不够多"。本次数据把这句话变成了定量事实：**13k 行代码、23 张表、9 个功能入口，对应 8 周里 1 篇写作。** 建造在系统性地替代使用（对独立开发者这是最舒服的拖延形式——每一天都很充实）。

三条具体建议：

1. **立一条使用纪律**，写进 PRD 或 todo：错题闭环数据层上线后，**每个 build session 之前先完成一个 15 分钟练习块**（一组 TCF drill 或一篇短写作）。自用产品的独特优势是 PM/用户/工程师同一人——数据不会说谎，下次审计直接看 attempts 表就知道纪律有没有执行。
2. **把"让练习发生"的最小集合排进本周**：配 Azure key（5 分钟）→ Readiness 卡片（0.5–1 天）→ 趋势图密度（0.5 天）。这三件事全部指向同一个问题："我练了有什么用、我现在到哪了"——这是练习动机的来源。
3. `/today` 维持在 error-loop 之后，但**不要再往后滑**——它是所有已建功能使用率的放大器，而使用率现在是全产品最短的板。
